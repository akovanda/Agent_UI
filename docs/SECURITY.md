# Security Model

Local AI Hub runs models that can generate convincing but incorrect instructions, consume untrusted
retrieved text, and—when Hermes or other tools are enabled—request actions against real systems.
The security boundary must therefore be enforced by ordinary infrastructure controls rather than by
model behavior.

## Trust boundaries

```text
Untrusted clients
      │
      ▼
Authenticated UI / reverse proxy
      │
      ▼
Gateway API key and profile policy
      │
      ├── untrusted prompts, uploads, and retrieved memory
      ▼
Model inference
      │
      ├── text only in the baseline
      ▼
Optional tool harness
      │
      ▼
Explicitly scoped credentials and approval gates
```

The model is never a security principal. A model saying that an action is safe, authorized, or
necessary does not grant permission.

## Baseline controls

1. **Loopback-only host publishing.** All Compose ports bind to `127.0.0.1` by default. Remote
   access should traverse Tailscale or an authenticated TLS reverse proxy.
2. **Separate secrets.** The gateway, memory-subject HMAC, Hermes API, and PostgreSQL database use distinct random
   secrets generated by `./hub init` inside the toolbox container.
3. **No secrets in Git.** `.env`, model weights, runtime databases, UI state, and Hermes state are
   ignored. Run a secret scanner before publishing any branch.
4. **One stable API boundary.** Clients use the gateway rather than receiving unrestricted direct
   access to llama.cpp. The direct llama.cpp port is for loopback diagnostics only.
5. **No tools in the gateway.** The baseline gateway routes text and memory but cannot execute
   shell commands, browse internal services, or mutate infrastructure.
6. **Memory is untrusted.** Retrieved memories are labeled as reference data rather than
   instructions before prompt injection.
7. **Principal and space isolation.** Memory identity comes from a validated Open WebUI JWT or a
   fixed-principal API key. Story/game spaces do not flow into personal assistant memory by
   default. Caller-selected username and namespace headers are not authorization inputs.
8. **Single request lease.** The T4 is serialized by default. This protects availability and avoids
   model-transition races; it is not an authorization mechanism.
9. **Review-first memory.** Automatic behavior is operator-opt-in, candidate memories are inactive
   until user approval, likely secrets are rejected, and rejected/expired proposal text is purged.
10. **Explicit bridges.** Cross-space reads require an operator-allowlisted direction and exact
    source plus target consent. Bridges are read-only and audited.

## Remote access

Preferred order:

1. Tailscale access to the host, leaving `BIND_ADDRESS=127.0.0.1` and using an SSH/Tailscale tunnel.
2. A private reverse proxy reachable only over Tailscale.
3. An internet-facing reverse proxy only when it provides TLS, strong authentication, rate limits,
   request-size limits, and regular patching.

Never expose llama.cpp or PostgreSQL directly to the internet. Do not expose SillyTavern without its
own access controls or an authenticated reverse proxy.

## Tool execution policy

Hermes and future Open WebUI tools must start from deny-by-default:

| Capability | Initial policy | Required before expansion |
|---|---|---|
| Read selected files | Allowlisted paths, read-only | Audit logs and path traversal tests |
| Write files | Disabled | Per-directory allowlists and approval |
| Shell | Disabled | Container sandbox, command policy, resource limits |
| SSH | Disabled | Dedicated low-privilege account, host allowlist, approval |
| GitHub read | Read-only token/app | Repository allowlist |
| GitHub write | Disabled | Explicit per-action approval and branch protection |
| Email/calendar | Disabled | Separate OAuth identity and send/create confirmation |
| Home automation | Disabled | Device allowlist and confirmation for physical actions |

A tool invocation should record: user, session, model/profile, tool name, normalized arguments,
approval outcome, start/end time, and result status. Redact credentials and message bodies where
possible.

## Prompt-injection defenses

Prompt injection cannot be solved solely with a system prompt. Use layered controls:

- label retrieved documents, web pages, email, and memory as untrusted data;
- never expose high-impact credentials to a model that only needs read access;
- validate structured tool arguments outside the model;
- require approval for mutations, external communication, purchases, account changes, and
  destructive commands;
- use allowlists for commands, paths, hosts, repositories, and APIs;
- cap tool loops, output sizes, wall time, CPU, memory, and network access;
- treat tool output as untrusted input on the next turn;
- include adversarial prompt-injection cases in the acceptance suite.

## Container hardening backlog

The initial Compose file prioritizes portability. Before granting tools or exposing the service
beyond a trusted network, add and verify:

- immutable image digests;
- `read_only: true` where supported;
- `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`;
- explicit tmpfs mounts;
- CPU/memory/PID limits;
- egress restrictions for tool containers;
- non-root users for every service that supports them;
- vulnerability scanning and a patch cadence;
- encrypted backups and tested secret rotation.

GPU containers may require exceptions; document each exception rather than broadening all services.

## Secret rotation

To rotate the gateway, llama.cpp, Open WebUI, Hermes API, and dashboard secrets:

1. create and protect a current backup;
2. stop external clients that cache API credentials;
3. run `./hub init --rotate-secrets`; this deliberately leaves the existing PostgreSQL password
   unchanged;
4. update manually configured clients such as SillyTavern;
5. recreate affected services with `./hub up --agent` as applicable;
6. verify old credentials fail and new credentials succeed;
7. record the rotation date without storing secret values.

The initialization command regenerates Hermes configuration in its Docker-managed volume. A
PostgreSQL password rotation is a separate database operation: update the role inside PostgreSQL,
then update `.env` and recreate all database clients. Do not merely change the environment value
for an existing cluster.

## Incident response

For suspected compromise:

1. disconnect remote access or stop the stack;
2. preserve relevant logs and timestamps;
3. rotate gateway, Hermes, database, proxy, and tool credentials;
4. review tool audit records and external account activity;
5. restore persistent data only from a known-good backup;
6. rebuild containers from pinned images;
7. add a regression test or policy control for the failure mode.

## Security acceptance criteria

- No service is reachable from another LAN host in the default configuration.
- Unauthorized gateway requests receive `401`.
- A forged user header or invalid forwarded JWT cannot select another user's memory.
- Personal memory is shared by eligible assistant experiences but not returned to story/game
  contexts.
- Hard purge removes provider source content and projections while retaining only content-free
  Agent UI audit metadata.
- A malicious memory entry cannot directly trigger a tool action.
- Tool mutations require a separately enforced approval decision.
- A secret scan finds no credentials, `.env`, UI state, model weights, or private keys in Git.
- Restore procedures do not accidentally publish secrets or private campaign data.
